Field dropdown order (labels EXACTLY as written, singular on purpose — his call, do not pluralize):

2. **Generation** — operator dropdown [is | is between | is unknown].

4. **Age** — operator dropdown [is | is between | is unknown].

   - is unknown -> no value input.
5. **Mom** — NO operator dropdown. One text box: contains-match on the person's mom's NAME.
   (Mom references are already validated to be female people, so this is a contains search

6. **Dad** — same as Mom but dad references are male people.
7. **Child** — operator dropdown [amount | amount range | name].
   - amount -> ONE number box (exact child count).
   - amount range -> TWO number boxes (inclusive count range).
   - name -> ONE text box: contains-match on any child's name.
8. **Sibling** — same three modes as Child (over index.siblingsOf).
9. **Spouse** — same three modes as Child (over index.spousesOf).
10. **Notes** — operator dropdown [has note | no note | note contains].
    - has note / no note -> no value input.
    - note contains -> ONE text box: contains-match over note text (case-insensitive).

Row shape: [field select] [operator select — ONLY for fields that have modes] [value area] [✕ remove].
Fields WITHOUT an operator dropdown render their single control directly: Name, Gender, Mom, Dad.
A brand-new row defaults to Name with an empty text box.

## Matching semantics — nail these exactly, they were chosen deliberately

- Blank text in ANY contains box (name, mom, dad, child/sibling/spouse name, note contains):
  the row is INERT (matches everyone) — same rule the current matchName already uses.
- Blank number in an "is"/"amount" box: row inert. Non-numeric junk in "is"/"amount": matches NOTHING.
- Range boxes ("is between", "amount range"): a blank or junk side means unbounded on that side
  (reuse the existing `bound()` helper semantics). Bounds are INCLUSIVE, applied as typed
  (never swapped — live filtering must not jump around mid-typing; this rule already exists).
- Generation 'is' with a typed number matches `Number(value)`; 'is unknown' matches people whose
  generation is the string 'unknown' (see MODEL CHANGE below). Inclusive between, blank side unbounded.
- Age 'is' matches numeric age equality; 'is unknown' matches age 'unknown'/null/undefined
  (current behavior); 'is between' inclusive with unbounded blank sides.
- Mom/Dad contains: resolve the mom/dad ID to the person via index.byId, then case-insensitive
  contains on displayName. If mom/dad is 'unknown' or 'none', a non-blank query does NOT match.
  Blank query = inert.
- Child/Sibling/Spouse: list lengths from index.childrenOf / siblingsOf / spousesOf.
  'name' mode: any listed person's displayName contains the query (blank = inert).
- Notes: 'has note' = noteViews(person).length > 0; 'no note' = 0; 'note contains' = any note's
  text contains the query, case-insensitive (blank = inert).
- Rows AND together (current filterByRows behavior — keep).
- Operator option labels exactly: "is", "is between", "is unknown", "amount", "amount range",
  "name", "has note", "no note", "note contains".

every person must stay visible (this app's entire purpose is listing everyone).

   `generation` = positive int OR the string 'unknown'.

3. app.js: keep unknown-generation people in state.people.
4. Tree layout: unknown-generation people must still appear. Group them in a trailing band after

   They have unknown parents, so no parent junction lines — same rendering as other standalone
   units. Check deriveUnions/grouping (family.js ~line 273 area and app.js ~lines 170-290) and
   make sure nothing divides or sorts on generation in a way that NaNs out on 'unknown'.
