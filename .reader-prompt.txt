## TASK C — name highlighting + tap-to-tree, with the repeated-name rule

For each verse, find occurrences of documented names (people from people.json):
- Match the person's display name as a case-insensitive whole phrase with word
  boundaries ("Adam" matches "Adam" and "Adam's", never "adament"; "Garrow Vell" only
  as the adjacent phrase). When names overlap, the longest match wins.
- Resolve each occurrence to exactly ONE person, in this order:
  1. Only one documented person has that name -> that person.
  2. Several share the name: if this exact verse ref IS one of their firstMention
     values (and exactly one person claims it), that person is the one addressed —
     a first-mention verse by definition names its person.
  3. Several share the name and it's a later verse: consult an optional
     data/mentions.json — {"<Book C:V>": {"<display name>": "<person id>"}, ...} —
     the phase-2 data-entry contract for repeated names. If the file exists, the node
     validator cross-checks its person ids and refs; the app fetches it once at boot
     (absent file = fine, treated as empty).
  4. Still ambiguous: DO NOT highlight the occurrence — render it as plain text.
     NEVER navigate to "just anyone with that name". Wrong-person navigation is worse
     than no navigation; the data contract (3) is how phase-2 entry resolves repeats.
- Implement the resolution as pure, unit-testable functions in family.js (ES5 style),
  exposed on the Family export (e.g. findNameOccurrences(verseText, index, verseRef,
  overrides) -> [{start, end, text, person}]), used by app.js for rendering.
- Tapping a highlighted name: close the reader, then reuse the EXISTING select-a-person
  flow (same as tapping a search result): highlight the person's card, scroll it into
  view, open their detail panel, set #person=<id>.
