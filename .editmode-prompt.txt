Bible Family Tree Explorer — add an EDIT MODE with auto-save.

IMPORTANT: MINIMAL changes only. Do not rewrite large sections. Add new code at the anchors below; do not restructure existing functions.

## Goal
The owner edits a person's info directly in the detail panel. Edits auto-save (debounced) to the server, which validates and writes the real data file (data/people.json). No save button — it saves itself and shows a small "Saved ✓" confirmation. Must work great on iPhone Safari (touch targets, no keyboard tricks, inputs with font-size ≥16px so iOS doesn't zoom).

## What to build

### 1. server.js — POST /api/people (core)
- In the route table: allow POST for `/api/people` only (everything else stays GET/HEAD with the existing 405). Call a new `handleApiPeoplePost(req, res)`.
- It must: read the body (cap at 2,000,000 bytes → 413 beyond), JSON.parse it (→ 400 on parse error), require `Array.isArray(body)` (→ 400), require every element to be an object, then validate with `require('./public/family.js').validate(body)` — if problems.length, respond 400 with `{ problems }`; if clean, write the file ATOMICALLY: write `DATA_FILE + '.tmp'` then `fs.renameSync` onto DATA_FILE, pretty-printed 2-space JSON + trailing newline. Respond `{ ok: true, count: N }` with the same no-store headers as GET.
- A failed write or any thrown error → 500 JSON, server stays up.

### 2. public/app.js — Edit mode in the detail panel
- Add an "Edit" button to the detail panel header area (next to the ✕ close button; find where the ✕ is wired in the `els` registry). Tapping Edit re-renders the panel in edit mode; a "Done" button returns to read-only view.
- Edit mode renders the SAME fields as inputs (use the `el()` helper, consistent with existing markup/classes):
  - Name: text input.
  - Gender: select male / female / unknown.
  - Generation: number input + an "unknown" checkbox (checked = "unknown").
  - Age: number input + an "unknown" checkbox (checked = "unknown").
  - Mom / Dad: each a select with options: `none`, `unknown`, then every existing female (for mom) / male (for dad) person by display name, excluding the person being edited. Values resolve to person ids.
  - Spouses: text input of comma-separated spouse NAMES; on save each name resolves to exactly one existing person (case-insensitive, exact match first, then unique contains; self and wrong-gender names are errors shown to the user).
  - Three compact selects for `spousesState`, `childrenState`, `siblingsState`: options known / none / unknown, current value preselected (absent = known). If the spouses list ends up non-empty, spousesState is forced to known (absent).
  - Notes: each note gets a textarea (its `text`), a text input (its `refs` as comma-separated references like "Genesis 2:7, Genesis 2:19"), and a small Remove button; an "Add note" button appends an empty note `{ text: "", refs: [] }`.
  - First mention stays read-only (shown as plain text in edit mode) — it is set by the Bible walk, not by hand.
- AUTO-SAVE: any input/change event schedules a save 800ms after the last change (debounce). The save: build the updated person from the form, apply spouse mutuality in BOTH directions across the whole array (add/remove on both sides), drop any note quote whose `ref` is no longer present in that note's refs, swap the updated person into a copy of `state.people`, then POST the full array to `/api/people`. On 200: flash a small "Saved ✓" chip inside the panel (fades after ~1.5s), then re-fetch `/api/people` and re-render through the EXISTING load/render path, keeping the edited person selected and staying in edit mode. On 400: render the returned `problems` list in a red error box at the top of the edit form (nothing is saved silently — the user sees exactly what is wrong and can fix it). On network failure: same box with a plain message. Also flush any pending debounced save when Edit/Done/close is used.
- Leave `renderDetail` (read mode) intact — edit mode is a separate render function alongside it, sharing the panel container.
